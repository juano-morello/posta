# Migrations — two flavors, one order

Every schema change lands in exactly one of two directories. Both are
applied by `pnpm migrate` (T1.5.1), in a FIXED order: **`drizzle/` first,
always, then `sql/`.**

## `migrations/drizzle/`

Generated by `drizzle-kit generate` (`pnpm --filter @posta/core run
db:generate`) from the Drizzle schema files under `packages/core/src/
schema/`. Applied by the programmatic drizzle migrator
(`runDrizzleMigrations`, `packages/core/src/db/client.ts`), tracked in
`drizzle.__drizzle_migrations` (drizzle's own table, keyed by a content
hash — see `migrations/drizzle/meta/_journal.json` for the filename ↔
hash ↔ timestamp mapping `pnpm migrate:status` reads).

This is where a schema change belongs whenever drizzle-kit can express it
as a plain `CREATE TABLE`/`ALTER TABLE` — ordinary tables, columns,
indexes, foreign keys, unique/check constraints on a non-partitioned
table.

## `migrations/sql/`

Hand-written `.sql` files, `NNN_name.sql` (three-digit, zero-padded,
lexicographic order — `001_events.sql`, `002_events_indexes.sql`, ...).
Applied by the hand-written runner (`runSqlMigrations`,
`packages/core/src/db/sql-migrate.ts`), tracked in
`_posta_sql_migrations(filename, checksum, applied_at)`.

This is where a schema change belongs whenever it needs SQL drizzle-kit
cannot generate. As of E1, that means three specific things:

- **`PARTITION BY`** — the `events` table (`001_events.sql`) is
  declaratively partitioned; drizzle-kit has no way to express
  partitioning at all, so both the parent table and every partition
  (`003_partition_fn.sql`'s `create_events_partition()`,
  `004_default_partition.sql`'s DEFAULT partition,
  `005_bootstrap_partitions.sql`'s initial monthly partitions) are
  hand-written SQL.
- **`CREATE FUNCTION`** — `create_events_partition(p_month date)`
  (`003_partition_fn.sql`) is genuine procedural SQL (PL/pgSQL), which
  drizzle-kit's schema DSL has no representation for at all.
- **`CREATE VIEW`** — not used yet in E1, but this is where E4's
  `events_classified` view (the read-time CASE over raw signals that
  computes the human/bot verdict, CLAUDE.md invariant 5) belongs: a view
  is not a table drizzle-kit's generator can emit, exactly like the two
  cases above. Improving a classification rule means editing that view
  in a NEW `sql/` migration — never a drizzle migration, and never an
  edit to an already-applied one (see the checksum rule below).

**The rule for deciding, in one sentence:** if `drizzle-kit generate`
can produce the DDL, it goes in `drizzle/`; if the change needs
`PARTITION BY`, `CREATE FUNCTION`, `CREATE VIEW`, or any other SQL
drizzle-kit's schema DSL cannot express, it goes in `sql/` as a new
`NNN_name.sql` file.

## Why drizzle runs first

`sql/`'s migrations are allowed to depend on tables/functions drizzle
owns — `005_bootstrap_partitions.sql` calls
`003_partition_fn.sql`'s own function (a same-flavor dependency), and a
future `sql/` migration (E4's `events_classified` view) will depend on
`asn_datacenter`, which is a plain drizzle-owned table (T1.4.1). The
reverse never happens — no `drizzle/` migration ever depends on
something `sql/` created. `pnpm migrate` (T1.5.1) enforces this order
as code, not just convention: it calls `runDrizzleMigrations()` before
`runSqlMigrations()`, unconditionally.

## The checksum rule: never edit an applied file, add a new one

`sql/` migrations are tracked by a SHA-256 checksum of their own content
(`sql-migrate.ts`'s `checksumOf()`). Re-running `pnpm migrate` against a
file whose checksum already matches its tracked row is a no-op — that is
what makes `pnpm migrate` idempotent. But if an ALREADY-APPLIED file's
content changes (someone edited `003_partition_fn.sql` after it shipped,
say), the checksum no longer matches, and `pnpm migrate` throws
immediately, naming the file, rather than silently re-running the edited
SQL or silently skipping it. There is no "update in place" for an applied
migration — the fix for a mistake in an already-applied file is always a
NEW migration (`006_fix_whatever.sql`) that corrects it, never an edit
to `003_partition_fn.sql` itself. `pnpm migrate:status` (T1.5.2) and CI's
`migrate-from-empty` job (T1.5.4) both surface this the same way: a
non-zero exit, naming the file.

Drizzle migrations have their own, separate version of this same rule —
drizzle-kit's own tooling owns editing/regenerating them; this document
and `sql-migrate.ts`'s checksum only govern `sql/`.

## Rolling back

Only the hand-written `sql/` flavor has a rollback tool
(`pnpm migrate:down`, T1.5.3) — one step, newest first, using a
migration's paired `NNN_name.down.sql` file. Not every `sql/` migration
has one (see `packages/core/migrations/sql/`'s own file list — some
migrations are not meaningfully revertible), and `pnpm migrate:down`
never touches `drizzle/` migrations at all; drizzle-kit's own tooling
owns those.
