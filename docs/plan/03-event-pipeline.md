# E3 — Event pipeline

**Milestone:** M1 · **Depends on:** E2 · **Unblocks:** E4

**Goal:** drain the queue, enrich, and land every event in Postgres **and** R2 — idempotently, in batches — with a proven ability to rebuild Postgres from R2.

**Done when:** 10k events pushed through end-to-end land exactly once in both stores, and the replay test rebuilds a truncated partition from R2 with row-for-row equality.

---

## S3.1 — Worker process & consumer

**As an** operator **I want** the worker isolated from the API **so that** analytics load can never touch redirect latency.

**Acceptance:**
- [ ] `apps/worker` is a standalone NestJS process, deployable and restartable independently
- [ ] BullMQ consumer with tuned concurrency
- [ ] Graceful shutdown: stop accepting, **flush the in-memory batch**, then exit — a rolling deploy must not eat the buffer
- [ ] Failed jobs retry with exponential backoff, then land in a dead-letter queue
- [ ] DLQ depth is alertable and inspectable
- [ ] Health endpoint reporting queue depth and last-successful-flush age

**Tasks:**

#### T3.1.1 · `feat: shared events queue contract in packages/core` ✅ done (`31434cd`)

## S3.2 — Enrichment (never judgement)

**As an** analyst **I want** derived fields computed once **so that** queries stay cheap — without ever deciding human-vs-bot here.

**The worker enriches; it does not judge** [INV-4]. Nothing in this story produces a verdict. If a task here starts to look like classification, it belongs in E4's view.

**Acceptance:**
- [ ] UA parse → `browser`, `browser_version`, `os`, `device_type`
- [ ] `source_platform` from referer + UA: Instagram · WhatsApp · TikTok · Facebook · X · directo
- [ ] `is_in_app` — UA contains `Instagram`, `FBAN`, `FBAV`, `TikTok`, `BytedanceWebview`, `Line`
- [ ] `dest_host` — destination host with query string stripped
- [ ] Unparseable UA yields nulls, never an exception — one weird UA must not stall a batch
- [ ] **No verdict is computed or stored anywhere in this path** [INV-4]
- [ ] Enrichment is pure and unit-testable without a database

## S3.3 — Batched idempotent Postgres writes

**As an** operator **I want** batched inserts that tolerate replay **so that** retries and backfills cannot double-count.

**Acceptance:**
- [ ] Flush on **100 events or 2000 ms**, whichever first
- [ ] One multi-row `INSERT ... ON CONFLICT (event_id, occurred_at) DO NOTHING` per batch [INV-8]
- [ ] The same batch applied twice produces the same row count — asserted in test
- [ ] Partial batch failure does not lose the whole batch: retry the batch, then split on repeated failure to isolate the poison row
- [ ] Poison rows go to the DLQ with their payload, never dropped silently
- [ ] Batch size and interval are env-configurable

**Tasks:**

#### T3.3.1 · `feat: batch accumulator with count and time triggers` ✅ done (`349f489`)
`BatchAccumulator` opens a batch on the first event, mints its `batch_id` ULID once (T3.4.3 keys the R2 object off it), and fires the injected flush callback at `EVENT_BATCH_SIZE` events or `EVENT_BATCH_INTERVAL_MS` since batch open, whichever first — both from the worker env schema (T0.3.6), defaulting to 100 and 2000. Exposes `flushNow()` for shutdown and `size()` for the health endpoint. No database here: the callback seam is what keeps the timing logic unit-testable with fake timers.
→ **files** `apps/worker/src/batch/accumulator.ts` · `apps/worker/src/batch/accumulator.test.ts` · **verify** `pnpm test accumulator.test.ts` with fake timers asserts 100 events flush at the 100th with no timer elapsed, 99 events flush at exactly 2000 ms, events added during an in-flight flush land in the next batch and are not lost, and `batch_id` is stable across the batch's lifetime · **after** T3.1.3, T0.3.6

#### T3.3.2 · `feat: multi-row insert with ON CONFLICT DO NOTHING` [INV-8] ✅ done (`5f7549e`)
`flushBatch(events)` first resolves each event's current destination with one batched `SELECT` keyed by `link_id` — `dest_host` needs the link's destination, which `CaptureEvent` does not carry, and `enrich()` is pure, so the SELECT must precede it — then enriches each event via T3.2.5 and issues a parameterised `INSERT INTO events (...) VALUES (...), (...) ... ON CONFLICT (event_id, occurred_at) DO NOTHING`, typed against `NewEvent` from T1.2.4. Both statements are batched for the whole flush, never one per event — the `ON CONFLICT` target is exactly the partitioned primary key, which is why the PK was shaped that way in T1.2.2.
→ **files** `apps/worker/src/batch/flush.ts` · `apps/worker/src/batch/flush.test.ts` · **verify** `pnpm test flush.test.ts` applies the same 100-event batch twice against a testcontainer and asserts one set of rows both times, that exactly TWO statements are issued per flush (one batched destination SELECT, then one batched INSERT) and never one per event, and that enrichment columns are populated · **after** T3.3.1, T3.2.5, T1.2.4

#### T3.3.3 · `feat: retry the batch, then split to isolate the poison row` ✅ done (`acc5d88`)
On insert failure the batch is retried whole with exponential backoff; on repeated failure it is binary-split and each half retried, recursing until a single failing event is isolated while every healthy event still commits. The naive alternative — drop the batch — loses 99 good events to punish one bad one, and the naive opposite — retry forever — wedges the queue.
→ **files** `apps/worker/src/batch/split-retry.ts` · `apps/worker/src/batch/split-retry.test.ts` · **verify** `pnpm test split-retry.test.ts` plants one event with an oversized `slug` in a batch of 100 and asserts 99 rows commit, the offending `event_id` is returned as poison, and the split performs O(log n) not O(n) round trips · **after** T3.3.2

#### T3.3.4 · `feat: send the poison row to the DLQ with its payload` ✅ done (`da8a8da`)
The isolated event from T3.3.3 goes to `EVENTS_DLQ_QUEUE` via `DlqService` carrying its full payload and the SQLSTATE, and the flush then reports success for the rest of the batch. Never a silent drop: a poison row that vanishes is an event Postgres and R2 will disagree about forever, with nothing to point at.
→ **files** `apps/worker/src/batch/split-retry.ts` · `apps/worker/src/batch/poison-dlq.test.ts` · **verify** `pnpm test poison-dlq.test.ts` asserts one DLQ entry containing the full event payload and a SQLSTATE, that the entry can be re-submitted through `flushBatch` after the underlying fault is removed, and that no event is dropped without a DLQ record · **after** T3.3.3, T3.1.5

#### T3.3.5 · `test: idempotency under overlapping and interleaved batches` [INV-8] ✅ done (`6b1134a`)
Beyond T3.3.2's same-batch-twice: partially overlapping batches, the same `event_id` split across two different batches, and concurrent flushes of overlapping sets. Asserts the final row count always equals the count of distinct `event_id` values. BullMQ is at-least-once, so overlap is the normal case, not the edge case.
→ **files** `apps/worker/src/batch/idempotency.test.ts` · **verify** `pnpm test idempotency.test.ts` asserts row count equals distinct `event_id` count across all three scenarios, and that the surviving row for a duplicated id is the first-written one · **after** T3.3.4

#### T3.3.6 · `perf: throughput benchmark for 10k events through the batch path` ✅ done (`842ccd0`)
Feeds 10k generated events through accumulator → enrichment → insert against a testcontainer, reporting events/sec, p95 flush duration and statement count. ## S3.4 — R2 append log

**As an** operator **I want** every event in an NDJSON log on R2 **so that** Postgres is a projection I can throw away and rebuild.

**Acceptance:**
- [ ] One R2 PUT per batch (never per event — R2 bills per PUT)
- [ ] Layout `events/dt=YYYY-MM-DD/hour=HH/<ulid>.ndjson`
- [ ] One JSON object per line, raw captured signals + enrichment, **no verdict, no IP** [INV-4][INV-6]
- [ ] R2 write failure retries; on exhaustion the batch goes to the DLQ **and Postgres is not committed either** — the two stores must not silently diverge
- [ ] Every event reaches Postgres **and** R2 [INV-7]
- [ ] Object keys are content-addressable enough that a replayed batch overwrites rather than duplicates

**Tasks:**

#### T3.4.1 · `feat: S3-compatible R2 client in packages/core/src/r2` ✅ done (`787d817`)
A single `S3Client` built from `R2_ENDPOINT`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` and `R2_BUCKET_EVENTS` (already validated in T0.3.6), with `forcePathStyle: true` so the same code addresses MinIO locally and R2 in production. Constructed once at module load, never per batch. [security] — credentials are read from env and never logged, including in the SDK's error paths.
→ **files** `packages/core/src/r2/client.ts` · `packages/core/src/r2/client.test.ts` · **verify** `pnpm test r2/client.test.ts` puts and re-reads an object against the compose MinIO from T0.4.4, and asserts a forced auth failure produces an error message containing no part of the secret key · **after** T0.4.4, T0.3.6

#### T3.4.2 · `feat: NDJSON serializer for event batches` [INV-4][INV-6] ✅ done (`9e00a07`)
`serializeBatch(events)` emits one JSON object per line, newline-terminated, UTF-8. Fields are copied through an **explicit allowlist** matching the `events` column set from spec §8 — not a spread — so a future extra field on the payload cannot silently reach the durable log. An `ip` or a verdict cannot appear in the log because the serializer has no key for one.
→ **files** `packages/core/src/r2/ndjson.ts` · `packages/core/src/r2/ndjson.test.ts` · **verify** `pnpm test ndjson.test.ts` asserts line count equals batch length, every line round-trips through `JSON.parse`, the emitted key set equals the `events` column list, and a payload with planted `ip` and `classification` keys serializes without them · **after** T3.2.5

#### T3.4.3 · `feat: partitioned R2 key scheme` ✅ done (`f1af8f2`)
`eventBatchKey(batchId, occurredAt)` → `events/dt=YYYY-MM-DD/hour=HH/<batchId>.ndjson`, always in UTC so a São Paulo `-03:00` timestamp partitions by its instant and not its local date. The key is derived from the `batch_id` minted once in T3.3.1, so every retry of the same batch PUTs to the same key and overwrites rather than duplicating.
→ **files** `packages/core/src/r2/keys.ts` · `packages/core/src/r2/keys.test.ts` · **verify** `pnpm test keys.test.ts` asserts `2026-07-21T02:30:00-03:00` produces `dt=2026-07-21/hour=05`, that hours are zero-padded, and that the same `batch_id` yields a byte-identical key across calls · **after** T3.4.2

#### T3.4.4 · `feat: one R2 PUT per batch from the flush path` ✅ done (`10c25e0`)
`flushBatch` serializes the batch and issues a single `PutObject`. One PUT per batch, never per event — R2 bills per PUT, and one object per click is real money at any volume, quite apart from turning a 10k-event burst into 10k round trips.
→ **files** `apps/worker/src/batch/flush.ts` · `apps/worker/src/batch/r2-put.test.ts` · **verify** `pnpm test r2-put.test.ts` flushes batches of 1, 100 and 100 against MinIO and asserts the PUT count is 3 and not 201, and that each object's line count matches its batch · **after** T3.4.3, T3.3.2

#### T3.4.5 · `feat: retry the R2 PUT and DLQ the batch on exhaustion` ✅ done (`f3bd70a`)
Exponential backoff over 5 attempts on retryable S3 errors (5xx, timeouts, throttling); non-retryable errors (403, 404 on the bucket) fail immediately since retrying a misconfiguration only delays the alert. On exhaustion the whole batch goes to the DLQ with its payload intact.
→ **files** `apps/worker/src/batch/r2-retry.ts` · `apps/worker/src/batch/r2-retry.test.ts` · **verify** `pnpm test r2-retry.test.ts` asserts a PUT failing twice then succeeding lands the object, that 5 failures produce one DLQ entry holding all 100 events, and that a 403 fails after a single attempt · **after** T3.4.4, T3.1.5

#### T3.4.6 · `feat: couple the two writes — no Postgres commit if R2 failed` [INV-7] ✅ done (`2f8ea40`)
Flush order becomes R2 PUT **then** the Postgres insert. If the PUT exhausts its retries, the transaction is never opened and the batch goes to the DLQ whole. The reverse order is the one that quietly kills invariant 7: Postgres would hold rows the log has never seen, and the "rebuildable projection" would rebuild into something smaller than what it replaced. The surviving asymmetry — R2 ahead of Postgres — is the recoverable one, because replay closes it.
→ **files** `apps/worker/src/batch/flush.ts` · `apps/worker/src/batch/coupled-writes.test.ts` · **verify** `pnpm test coupled-writes.test.ts` stops the MinIO container mid-run and asserts zero new rows in `events`, one DLQ entry, and that after MinIO returns the DLQ entry replays into both stores · **after** T3.4.5

#### T3.4.7 · `test: both stores agree after 10k events` [INV-7] ✅ done (`e3ce531`)
Pushes 10k events, drains, lists every NDJSON object in the covered hour prefixes, and compares the `event_id` set against Postgres **in both directions** — a one-directional check passes while Postgres silently holds extra rows, which is exactly the divergence T3.4.6 exists to prevent.
→ **files** `apps/worker/src/batch/reconciliation.test.ts` · **verify** `pnpm test reconciliation.test.ts` asserts the two sets are equal, that the symmetric difference is empty in both directions, and that each event's enrichment fields match between the NDJSON line and its row · **after** T3.4.6

> Coupling the two writes is the point of invariant 7. If Postgres commits while R2 fails, the "source of truth" quietly stops being the source of truth, and nothing tells you.

## S3.7 — What the close-out found

**As an** operator **I want** the gaps E3's own close-out verification surfaced closed **so that** the pipeline's shipped behaviour matches the design its tasks describe, instead of merely containing it.

This story is not new scope. Every item was confirmed against real code at close-out (`343d0c0`, 2026-07-29) and each one names the file it was found in. Two of them are capabilities that were built, reviewed, tested and never called; the rest are places where a value is validated and never read, or a check fires on the wrong condition. All six passed E3's full test suite — which is the finding, not an aside. Closing them takes eleven tasks.

**Acceptance:**
- [ ] A poison row costs one row, not the batch — `retryWithSplit`/`sendPoisonEventsToDlq` have a production call site a `grep` can find
- [ ] A split's sub-batches each write to their own stable R2 key: a retry overwrites itself and never a sibling [INV-7]
- [ ] A database outage is never mistaken for a poison row, so an outage cannot mass-dead-letter a batch
- [ ] The worker addresses a real R2 account with `R2_ENDPOINT` empty, and refuses to boot when it can address neither
- [ ] `WORKER_CONCURRENCY` and `EVENT_BATCH_SIZE` are checked against each other at boot — a pair that can never fill a batch warns loudly and never blocks the boot — and `.env.example` satisfies the schema it documents
- [ ] No DLQ entry stores the value of an invariant-6 forbidden key, and the DLQ is bounded in size [INV-6]
- [ ] A worker with an empty queue and an empty accumulator reports healthy, however long it has been idle

**Tasks:**

#### T3.7.1 · `feat: retryWithSplit keys every sub-batch off the batch's own batch_id` [INV-7][INV-8] ✅ done (`09da955`)
`retryWithSplit` calls `flushBatch(events)` with one argument (split-retry.ts:181), so every attempt mints a fresh `newId()` inside `createFlushBatch` and lands at a new R2 key — flush.ts:107-119 records this as a known consequence, dormant only because nothing calls `retryWithSplit`. T3.7.3 ends the dormancy, so the id threads through one commit *ahead* of the wiring rather than after it: the other order puts a live re-keying window on `main` for exactly one commit, and stable re-keying is the whole property T3.4.3 exists to provide. The id is **derived** per sub-batch rather than inherited whole — the root uses the accumulator's `batch_id`, each half appends `.0`/`.1` to its parent's — because both halves of a split issue their own PUT, and handing both the parent's id makes the second silently overwrite the first, leaving R2 holding half a batch while Postgres holds all of it: invariant 7's one forbidden asymmetry, introduced by the mechanism meant to protect against it. `eventBatchKey` states outright that it does not validate the id's shape, so a suffixed id is a key change and not a schema change. `batchId` joins `SplitRetryOptions` as **optional**, defaulted once at the top of `retryWithSplit` to a single `newId()` the whole recursion then derives from — deliberately not required, because required breaks `poison-dlq.test.ts`'s two existing `SplitRetryOptions` call sites (lines 185, 244) to buy nothing: one default evaluated once, outside the recursion, still means nothing *inside* the recursion mints an id, which is the property that matters. The cost, recorded rather than hidden: a split batch leaves the root object plus one object per sub-batch, holding overlapping records — duplicate objects, never missing ones, and replay's `ON CONFLICT DO NOTHING` [INV-8] makes a duplicate record cost a skipped row and nothing else. Worth stating as a number, because the worst case is not small: a fully-poisoned 100-event batch splits into 199 sub-batches, so 199 distinct R2 objects and ~398 PUTs carrying ~700 duplicated records, to land zero rows — against S3.4's own acceptance criterion, "One R2 PUT per batch (never per event — R2 bills per PUT)", which a full split exceeds by roughly 4×. That is a bill, not a correctness bug, and T3.7.2 is what keeps the pathological case unreachable: a batch where every row fails is an infrastructure failure, and an infrastructure failure never splits.

#### T3.7.2 · `feat: classify a flush failure before splitting it`
Splitting assumes the failure belongs to a row. A Postgres outage fails every sub-batch equally, so the binary search runs all the way down and declares **every event in the batch poison** — a recoverable outage converted into a mass dead-letter, the day T3.7.3 makes the split live. `classifyFlushError(error)` is therefore a **closed allowlist**, not an open one: it returns `'row-fault'` for exactly SQLSTATE classes 22 (data exception) and 23 (integrity constraint) — the only two whose failures genuinely belong to one row — and `'infrastructure'` for **everything else**. That "everything else" is the load-bearing half. Class 42 belongs to it: a missing column, an unapplied migration or a lost INSERT grant is a property of the statement, not of any row, and no binary search can isolate one — a class-42 row-fault verdict splits to singletons and dead-letters every event, which is precisely the outcome this task exists to prevent. `42501 insufficient_privilege` is not hypothetical here: env.ts:13-16 already records that the writer/reader privilege split lands in T4.2.4, and a rolling deploy where the worker starts before its migration finishes raises class 42 on every INSERT. Classes 08/53/57/58 belong to it too, as do class 40's transient rollbacks (`40001`, `40P01 deadlock_detected`), an unrecognised SQLSTATE, and any error carrying no SQLSTATE at all. Enumerating "infrastructure" instead would leave every class nobody thought of — 25, 55, XX — falling through to `'row-fault'`, which is the mass-dead-letter again, arrived at by omission.
An infrastructure verdict makes `retryWithSplit` retry the whole sub-batch and then **reject**, which is a deliberate change to its contract — split-retry.ts's own header ("never throws for a partial failure") is amended in the same commit, because an infrastructure failure is not a partial failure. The observable production behaviour is unchanged from today's: the flush rejects, the accumulator's waiters reject, and BullMQ redelivers. When a *sub*-batch classifies infrastructure mid-recursion, after a sibling has already committed, the throw out of `attemptBatch` (split-retry.ts:214-220) discards `leftResult` including any poison it had already isolated. That is the accepted behaviour and not an oversight: BullMQ redelivers the whole job, T3.3.3's `ON CONFLICT DO NOTHING` makes the committed half's re-flush free, and the isolation work is simply redone. It is stated here so an implementer does not invent a partial-result-preserving alternative. It arrives as an injected `SplitRetryOptions` predicate, defaulted, never as a branch inside `attemptBatch`: split-retry.ts's own header states that the algorithm parses no SQLSTATE and inspects no Postgres error shape, and that stays true when the knowledge lives behind the same kind of seam `sleep` and `logger` already use. `classifyR2Error` (r2-retry.ts) is the in-repo precedent for the shape, and `extractSqlState`'s bounded `Error.cause` walk moves out of dlq.service.ts into the new module and is imported back, never copied — drizzle wraps the real `pg` error, so both callers need the identical walk. What will NOT catch a regression here: T3.5.6's own outage is a `docker pause`, where a query hangs rather than rejects (that file's header, lines 74-100 — "nothing ever REJECTS"), so no rejection means no split, with or without this classifier. The risk is real but its shape is a managed-Postgres failover or restart, which rejects with class 08/57. This task's own table-driven test is the discriminating one.

#### T3.7.7 · `feat: warn at boot when WORKER_CONCURRENCY cannot fill EVENT_BATCH_SIZE`
Since T3.5.4 a job is held open until its batch flushes, so at most `WORKER_CONCURRENCY` events can occupy the accumulator at once and the count trigger can never fire while concurrency is below `EVENT_BATCH_SIZE` — every batch waits out the full interval and flushes at ~8 events instead of 100. `.env.example` ships exactly that pair (`EVENT_BATCH_SIZE=100` against an unset `WORKER_CONCURRENCY` defaulting to 8), so the documented configuration silently underperforms its own documentation, and `apps/worker/src/env.ts` has no cross-field rule to say so. The fix is a **loud startup warning, never a boot failure**, and that distinction is the whole design decision. "Batch size above concurrency" is a legitimate configuration: it means "flush on interval only", which is a perfectly reasonable choice for a low-traffic deployment — bounded latency, smaller batches, fewer held job locks. Failing the boot would convert a performance note into an availability failure, and it would break three configurations that exist today, two of which choose the outlawed pairing *deliberately*: `sigterm-flush.test.ts` runs `EVENT_BATCH_SIZE=500` against `WORKER_CONCURRENCY=250` and its own header (lines 84-86) says the pairing is the mechanism — "keeps the count trigger from ever firing"; `e2e-kill-recovery.test.ts` does the same with 500 against 15 and 45; and `.github/workflows/images.yml:104` writes a `.env` with `EVENT_BATCH_SIZE=100` and no `WORKER_CONCURRENCY` at all. #### T3.7.8 · `feat: forbidden-key redactor for invariant-6 payloads` [INV-6][security] ✅ done (`75e5f2e`)

#### T3.7.10 · `feat: bound DLQ retention with a throttled clean of aged entries` [INV-6][security]
`dlqQueue.add()` is called with no job options at all, unlike `EVENTS_QUEUE`'s own `EVENTS_JOB_OPTIONS`, so the DLQ grows without bound in a Redis configured `volatile-lru` — where a key with no TTL is also a key the eviction policy will never reclaim. The obvious fix does not work and must not be attempted: `removeOnComplete`/`removeOnFail` apply only when a job reaches a terminal state, and nothing drains `EVENTS_DLQ_QUEUE`, so every entry sits in `wait` forever and no job option will ever fire. `Queue.clean(grace, limit, 'wait')` does apply to waiting jobs (checked against the installed bullmq@5.80.10 typings), so `send()` performs an opportunistic, limit-bounded clean after a successful write, at most once per throttle window — piggybacking on the write path because the queue only grows when something writes to it. The rejected alternative, a scheduled maintenance job, needs the BullMQ scheduler `partition-maintenance.job.ts` registers and that nothing in `AppModule` wires up, so retention would have shipped as a second orphan of exactly the kind T3.7.3 exists to fix. The clean runs **after** the `add()` resolves, not before it — which decides the boundary case, because `Queue.clean` computes `timestamp = Date.now() - grace` and `cleanList.lua:35` deletes any job whose `jobTS <= timestamp`, so with the window at zero the just-written entry is itself old enough to be deleted. A `clean()` rejection is logged and never propagates into `send()` — the DLQ write matters more than the trim — and it is logged, not swallowed. The window itself is a module constant with a test-only optional constructor override, not a second injected provider: `DlqService`'s only constructor parameter today is `@InjectQueue(EVENTS_DLQ_QUEUE)` (dlq.service.ts:256-258), and a second injected value needs a provider registered in `app.module.ts` — a file this task deliberately does not touch, since T3.7.3 is already changing it in the same story. The cost, recorded rather than hidden: a cleaned entry is gone. A `'flush-poison'` event still exists in R2 — its PUT succeeded before the INSERT failed — though replay cannot land it (T3.7.3); a `'schema-validation-failed'` payload never reached R2 at all and is destroyed outright, and poison-dlq.test.ts:231-238 already asserts that the DLQ entry is the only place it exists. The window is therefore sized against S3.1's own "DLQ depth is alertable" criterion — long enough that an operator can act on the alert before the evidence expires — not against Redis memory alone. The rejected alternative is a **count** cap (drop oldest beyond N), which preserves recent evidence under a burst where an age cap does not; age wins here only because it is the one BullMQ's `clean` implements natively, and a count cap would mean reimplementing eviction over `wait` by hand.

#### T3.7.11 · `fix: an idle worker with an empty queue is healthy, not stale` ✅ done (`6944cad`)
The accumulator's interval timer only runs while a batch is open, so `lastFlushAgeMs()` grows unbounded through a genuine traffic lull, and `isStale` has no queue-depth gate — more than 6 seconds of zero traffic at the shipped `EVENT_BATCH_INTERVAL_MS` answers 503 for a worker that is not stuck, only idle, and a Kubernetes probe will act on that. The gate is `queue_depth > 0 || batch_size > 0`, and `queue_depth` is the load-bearing term: a wedged flush leaves every job whose event it holds stuck in BullMQ's `active` set (jobs are held open until `add()` settles, T3.5.4), and `active` is one of the states counted — `QUEUE_DEPTH_JOB_TYPES`, health.controller.ts:59. `batch_size` is belt-and-braces for the window where a batch is open but its jobs have not yet been counted. It is explicitly **not** the wedged-flush signal, and the reason has to be written down or someone will re-derive the wrong justification: `BatchAccumulator.size()` reads the OPEN batch only and "never reflects a batch that has already been detached to an in-flight flush" (accumulator.ts:270-279), so during a wedged flush it reads 0. In production `batch_size > 0` therefore implies `queue_depth > 0` — the second term costs nothing and closes a race, but the first is what makes the gate correct. T3.1.7's own 503 case currently plants `queue_depth: 0`, so that test is re-planted with a non-zero depth — the behaviour changed deliberately, the assertion is not being weakened, and T3.1.7's verify sentence ("503 after advancing fake timers past the threshold") stays literally true.
